# Gate Proofs

Every Gate was proven by introducing the violation named in its Gate Contract, running the Entry Point of its tier (`make check-fast` for fast Gates, `make check` for full Gates) with only the change under proof present, confirming it exited non-zero and named the Gate, then restoring the tree.

The Entry Point is the same command in every proof of a tier, and the tree is not: each run carries exactly one behavioral violation, which is why a red result can be laid at the Gate the Entry Point named. The proof script owns that reasoning and the checks it needs; what this page records is the outcome of one complete run.

A Gate Proof is defined in the [glossary](../../GLOSSARY.md); the report a run produces is execution evidence about the tree it ran against, and a previous report cannot establish that the current tree still works, so the report is not versioned. The [proof runner](scripts/gate-proofs.mjs) writes its report under `reports/`, which Git ignores, and a single-Gate iteration leaves the last complete report in place. To obtain current evidence, dispatch the [`gate-proofs` workflow](../../.github/workflows/gate-proofs.yml) from the Actions tab and download the report artifact from that run; the workflow file is the authority on how the baseline is validated and the report is published, and the run page ties the artifact to its tested commit.

The cost is one Entry Point run per Gate - the full tier's container, mutation run and advisory lookup included - and it is paid deliberately, which is why neither Entry Point runs a proof and why a single proof can be re-run alone. Each proof also records the changes its violation left in the tree, so the claim that only that violation was present is checkable rather than asserted.

A changed-set Gate needs its input to exist, and the branch a proof runs on may change none of it. So the Mutation proof declares the smallest eligible scope its violation needs - here the core domain file whose test the proof weakens - beside the proof definition in [the proof runner](scripts/gate-proofs.mjs). That declaration is setup, not a second violation: it is not a source marker, and the weakened test stays the only deliberate fault. The obligations such a declaration must meet are the Gate Proof rules in [GATE-CONTRACTS.md](../../skills/bootstrap-harness/GATE-CONTRACTS.md); what is particular here is that it replaces the changed set through [the Mutation wrapper](scripts/check-mutation.mjs) for that one execution, travels in the environment of that run, and is accepted only when the analyzed files are exactly the declared ones and the analysis completed - so a partly covered input, a wider analysis, or a tool failure cannot be mistaken for the proof.

Each proof's record carries the requested and the analyzed scope beside the evidence its Contract asks for; here the scope is read from the Gate's own record of its analysis rather than from its logged output, so shortening that output cannot erase it. Ordinary changed-set selection - including the legitimate empty set of a documentation-only branch, the unresolvable-base widening, and the scheduled whole-codebase run - keeps the behavior its Contract describes, and is checked separately: [the focused checks](test/harness/mutation-scope.test.mjs) drive the wrapper against controlled Git trees, and [the proof checks](test/proofs/gate-proof-evidence.test.mjs) drive the proof runner against a stand-in Entry Point. The `gate-proofs` workflow runs both before the proofs, and neither Entry Point runs either. An explicit-scope proof establishes enforcement and Entry Point wiring, not correctness of Git-based discovery, which is what those checks are for.

Before the E2E row was recorded, the level was also exercised by hand with five deliberate faults: a failing assertion, an undefined step, a pending step, no selected scenarios, and no compiled artifact. Each made the Gate exit non-zero. Cucumber's strict mode covers the assertion, undefined and pending cases; `scripts/run-e2e.mjs` covers the empty selection; the readiness wait covers the missing artifact.

## Validation modes

`make check` is validation by change and `make check MODE=integral` is integral validation; the check list, impacts, scopes, costs, budget and periodic cadence live in [harness/policy.json](harness/policy.json), and [ADR 0006](docs/adr/0006-validation-modes.md) records why. A green validation-by-change result states the checks it ran, their scopes, the checks that did not apply and the periodic checks it left to integral validation; it does not claim integral verification. The whole-codebase mutation is the periodic check: validation by change reports it, integral validation runs it, and a failure in its scope keeps a change in that scope from reporting green while a demonstrably independent change proceeds.

The modes are rehearsed on a disposable copy with a controlled budget fixture by [scripts/rehearse-validation.mjs](scripts/rehearse-validation.mjs), run with `npm run rehearse-validation` and not part of either Entry Point. The rehearsal copies the project to a temporary directory, replaces the policy with a small fixture whose checks record the scope they were asked to verify, and drives `make check` and `make check MODE=integral` there. It demonstrates, and asserts, that:

- a violation in an affected dependent is caught, with the dependent in the scope the check was asked to verify, and not merely listed;
- a shared dependency change widens the selection, and required validation beyond the fixture's approved budget exits non-zero with an inconclusive result while starting no check;
- a green validation-by-change result reports the periodic check it omitted and does not claim integral verification;
- integral validation actually runs that periodic check and records its result;
- a periodic integral failure stays visible, a change in its scope is not reported green and requires treatment, and an independent change proceeds with the failure reported.

The rehearsal's transcript is run output: the script prints it and writes it under `reports/`, which Git ignores. Its fixture is deliberately tiny, so it demonstrates the policy's behaviour and says nothing about durations on a production-sized application; each adoption measures its own budget against its own tree. The run recorded here (commit `37c69f8`) printed `Rehearsal: every expectation held.`

The table is history, not current evidence: a row says what a Gate did to the tree of that run, and no row speaks for a later change. The explicit-scope Mutation proof was re-run on its own after the change that introduced it, on a branch that changed no eligible Mutation input. That run printed:
